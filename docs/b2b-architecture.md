# B2B Συνεργατών — Αρχιτεκτονική (Φάση 1: πύλη, πρόσβαση, ερωτηματολόγιο, σύνδεση)

> Κατάσταση: σχέδιο, χωρίς κώδικα. 31/10/2026.
> Στόχος τελικός: διαθεσιμότητα των προϊόντων στα καταστήματα των συνεργατών μέσα στο eshop μας.
> Στόχος αυτής της φάσης: να υπάρχει ο συνεργάτης ως οντότητα, να μπαίνει στο B2B, να απαντά ερωτηματολόγιο,
> να διαμορφώνει το προφίλ των καταστημάτων του και να διαλέγει/ελέγχει τρόπο διασύνδεσης. Οι connectors
> υλοποιούνται ένας-ένας στις επόμενες φάσεις πάνω στο ίδιο πλαίσιο.

## 1. Τι υπάρχει ήδη και τι ξαναχρησιμοποιούμε

| Υπάρχον | Χρήση στο B2B |
|---|---|
| `Store` (γεωγραφικά, ωράριο, υπηρεσίες, φωτογραφία, `member` ως κείμενο, `erpBranch`) | Μένει ως έχει· αποκτά `partnerId`. Το `member` αντικαθίσταται σταδιακά από τη σχέση. |
| `StoreStock (variantId, storeId, qty)` | Ο τελικός προορισμός του στοκ. Επεκτείνεται με πηγή και φρεσκάδα (Φάση 2+). |
| `Staff` + RBAC (`Role/Permission`, `can()`), `AuditLog` | Διαχείριση από εμάς· νέα δικαιώματα `b2b.*`. Οι χρήστες B2B **δεν** είναι Staff. |
| OTP/throttle (`lib/auth/otp`, `throttle`), `PasswordReset` (pattern) | Ίδιο pattern για είσοδο/ανάκτηση κωδικού B2B. |
| `ApiKey` (hash, scopes) | Κλειδί ανά συνεργάτη για τη μέθοδο «μας στέλνετε εσείς» (push API). |
| XML wizard προμηθευτών (`SupplierFeed`, `FeedSnapshot`, `lib/catalog/xml-import`) | Ίδια λογική αντιστοίχισης στηλών + στιγμιότυπο για feeds XML/CSV των συνεργατών. |
| Σειρά προς SoftOne (`ErpSync` pattern: preview → queued → sent/failed) | Outbox για εγγραφή συνεργάτη/καταστημάτων/επαφών στο SoftOne. |
| `lib/help` + `data-help` | Κάθε νέα σελίδα admin παίρνει οδηγό· οι σελίδες επαφών μπαίνουν στη λίστα `PII` των help-shots. |

## 1Α. Διάταξη συστημάτων: κεντρικό site + χωριστή μηχανή διαθεσιμότητας

**Απόφαση (31/10/2026):** η μηχανή διαθεσιμότητας είναι **χωριστή υπηρεσία με δική της βάση και δικό της subdomain**. Η διαχείριση, το reporting, η πιστοποίηση των μελών και η πύλη B2B μένουν στο κεντρικό site. Η τρέχουσα διαθεσιμότητα (projection) ζει **και** στο κεντρικό, γιατί από εκεί δρομολογείται η παράδοση/αποστολή από το κοντινότερο κατάστημα.

### Γιατί
- **Φορτίο**: ~320 υποκαταστήματα × χιλιάδες κωδικοί το καθένα, ανανέωση κάθε λίγα λεπτά. Αυτό σημαίνει εκατομμύρια γραμμές και συνεχείς εγγραφές. Ο Postgres του eshop είναι **κοινός με άλλα 6 projects** (όριο 100 συνδέσεις, PgBouncer), οπότε δεν πρέπει να επιβαρυνθεί.
- **Απομόνωση βλαβών**: αν ένα ERP μέλους κολλήσει ή αργήσει, δεν επηρεάζει το eshop. Χωριστό deploy στο Coolify, χωριστή κλιμάκωση των workers.
- **Ασφάλεια**: τα διαπιστευτήρια των ERP/eshop των μελών ζουν **μόνο** στη μηχανή, μακριά από τη βάση με τα προσωπικά δεδομένα πελατών. Αν διαρρεύσει η μία βάση, δεν διαρρέουν και τα δύο.
- **Δημόσιο endpoint**: το push API (`POST /v1/stock`) δέχεται κίνηση από 300 τρίτα συστήματα. Καλύτερα σε χωριστό host με δικά του όρια ρυθμού, όχι μπροστά από το checkout.

### Ποιος κάνει τι

```
                   euronics.gr (κεντρικό, Postgres «euronics»)
 ┌──────────────────────────────────────────────────────────────────────┐
 │ Eshop · Admin · Πύλη B2B (/b2b) · Πιστοποίηση μελών (realm B2B)      │
 │ Master: Partner, Store(=TRDBRANCH), Contact, B2bAccount,             │
 │         ερωτηματολόγιο, προφίλ, κατάλογος (Variant, EAN, MPN)        │
 │ Read model: StoreAvailability (μόνο ό,τι χρειάζεται το eshop)        │
 └───────▲─────────────────────────────┬────────────────────────────────┘
         │ ② projection διαθεσιμότητας  │ ① γεγονότα: partner/store/connection
         │   (batch upsert, υπογεγραμμένο) │   άλλαξαν, κατάλογος ταυτοτήτων
         │                             ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ stock.euronics.gr: μηχανή διαθεσιμότητας (Postgres «euronics_stock», │
 │ άλλο instance)                                                       │
 │ Connectors + scheduler/workers · push API · έλεγχος σύνδεσης         │
 │ Secrets (κρυπτογραφημένα) · ακατέργαστα στιγμιότυπα · ιστορικό runs  │
 │ Αντιστοίχιση προϊόντων (PartnerProductLink) · LocationMap            │
 └───────▲──────────────────────────────────────────────────────────────┘
         │ pull (API / feed / SFTP)  ή  push από τα μέλη
   ERP / eshop μελών (SoftOne, Entersoft, Epsilon, Galaxy, Woo, …)
```

### Οι τρεις διεπαφές
1. **Κεντρικό → μηχανή (γεγονότα)**: «άλλαξε συνεργάτης / κατάστημα / σύνδεση», και ο **κατάλογος ταυτοτήτων** (variantId, EAN, MPN, μάρκα, ο κωδικός μας), όχι τιμές ή περιγραφές. Outbox στο κεντρικό, παραλαβή idempotent στη μηχανή.
2. **Μηχανή → κεντρικό (projection)**: συμπυκνωμένη διαθεσιμότητα ανά `(variantId, storeId)`: κατάσταση (`in` / `low` / `out`), ποσότητα σε κλίμακα (όχι ακριβής, αν το ζητά το μέλος), `seenAt`. Μόνο για αντιστοιχισμένα προϊόντα και μόνο όταν αλλάζει (diff). Αυτό τροφοδοτεί σελίδα προϊόντος, χάρτη, φίλτρο «διαθέσιμο κοντά μου» και click & collect χωρίς δικτυακή κλήση ανά προβολή σελίδας.
3. **Κεντρικό ↔ μηχανή (εντολές, server-to-server)**: η πύλη B2B και το admin καλούν API της μηχανής για «αποθήκευσε διαπιστευτήρια», «έλεγξε σύνδεση», «δείξε runs / αταίριαστα / έγκρινε αντιστοίχιση». Υπογραφή HMAC + λίστα επιτρεπτών IP. Ο browser **δεν** μιλά απευθείας με τη μηχανή, άρα ένα μόνο login, στο κεντρικό.

### Πιστοποίηση: μόνο στο κεντρικό
- Τα μέλη, το προσωπικό και οι πελάτες κάνουν login **μόνο** στο κεντρικό (realm B2B, §3). Η μηχανή **δεν έχει χρήστες ούτε σελίδα εισόδου**.
- Η μηχανή αναγνωρίζει μόνο **συστήματα**:
  - το κεντρικό, με υπογραφή HMAC και λίστα επιτρεπτών IP,
  - τα ERP των μελών που μας στέλνουν στοκ, με κλειδί API ανά σύνδεση. Το κλειδί το εκδίδει και το ανακαλεί το κεντρικό και η μηχανή κρατά μόνο το hash του.
- Αν ένα μέλος απενεργοποιηθεί στο κεντρικό, το γεγονός ① ακυρώνει αμέσως τα κλειδιά και σταματά τους workers του.

### Δρομολόγηση παράδοσης από το κοντινότερο κατάστημα
Γι' αυτό η διαθεσιμότητα **πρέπει** να υπάρχει στο κεντρικό: εκεί ζουν η παραγγελία, το checkout, τα μεταφορικά και οι κανόνες.
1. **Πρόταση (checkout)**: από το `StoreAvailability` + τη γεωγραφική θέση του πελάτη (ή τον ΤΚ) → υποψήφια καταστήματα με απόσταση, φρεσκάδα στοιχείου, υπηρεσίες (παραλαβή, παράδοση, τοποθέτηση) και κανόνες μέλους (ακτίνα παράδοσης, ελάχιστη αξία, ώρες).
2. **Επιβεβαίωση τη στιγμή της παραγγελίας**: το αντίγραφο μπορεί να είναι λίγων λεπτών. Πριν από την πληρωμή, το κεντρικό ζητά από τη μηχανή **live έλεγχο** για το συγκεκριμένο προϊόν και κατάστημα, όπου ο connector το υποστηρίζει. Αλλιώς το επιβεβαιώνει το μέλος από την πύλη, με προθεσμία.
3. **Ανάθεση**: η παραγγελία (ή γραμμή της) ανατίθεται σε κατάστημα. Το μέλος βλέπει και αποδέχεται την ανάθεση στην πύλη B2B. Αν απορρίψει ή λήξει η προθεσμία, πάει στο επόμενο κατάστημα ή στην κεντρική αποθήκη.
4. **Αποστολή/παράδοση**: από το κατάστημα με δική του παράδοση ή με courier από τη διεύθυνσή του (ΕΛΤΑ κ.λπ., ήδη υλοποιημένα), και ενημέρωση του πελάτη.
5. **Συμψηφισμός**: παραστατικό προς το μέλος στο SoftOne. Θα σχεδιαστεί χωριστά, σε σχέση με τις εγγραφές παραγγελιών eshop που υπάρχουν ήδη.

Η δρομολόγηση είναι **επόμενη φάση**. Από τώρα όμως το `StoreAvailability` σχεδιάζεται με ό,τι θα χρειαστεί: `storeId`, κατάσταση, ποσότητα ή κλίμακα, `seenAt` και αν υποστηρίζεται live έλεγχος.

### Πώς ενώνεται με το eshop
Το «κεντρικό» **είναι** η εφαρμογή του eshop (ίδιο Next.js, ίδια βάση). Η μηχανή δεν αγγίζει ποτέ σελίδες. Απλώς γεμίζει έναν πίνακα του eshop.

**Κοινά κλειδιά** (τα ορίζει το eshop, η μηχανή τα αντιγράφει): `variantId` για το προϊόν, `storeId` για το υποκατάστημα, `partnerId` για το μέλος. Η μηχανή μεταφράζει τους δικούς τους κωδικούς προϊόντων και αποθηκών σε αυτά (`PartnerProductLink`, `LocationMap`), οπότε στο eshop φτάνουν ήδη «δικά μας» προϊόντα και καταστήματα.

**Διαδρομή ενός στοιχείου στοκ**
```
ERP μέλους ─(pull/push)─> μηχανή: αντιστοίχιση → diff ─(batch, υπογεγραμμένο)─> eshop: StoreAvailability
                                                                             └─> σβήνει cache των σχετικών σελίδων
```

**Πού φαίνεται στο eshop**
| Σημείο | Τι διαβάζει από το `StoreAvailability` |
|---|---|
| Σελίδα προϊόντος | «Διαθέσιμο σε Ν καταστήματα κοντά σας», με λίστα και χάρτη, απόσταση, «ενημέρωση πριν από Χ′» |
| Λίστες/αναζήτηση | φίλτρο «Διαθέσιμο κοντά μου» / «Παραλαβή σήμερα» (facet με βάση ΤΚ ή τοποθεσία) |
| Σελίδα καταστήματος (`/katastimata/[slug]`) | προφίλ του μέλους + «διαθέσιμα εδώ» |
| Καλάθι/checkout | επιλογή «παραλαβή από κατάστημα» / «παράδοση από κατάστημα», live επιβεβαίωση (βήμα 2 παραπάνω) |
| Παραγγελία | ανάθεση σε κατάστημα, κατάσταση από την πύλη B2B, ειδοποιήσεις στον πελάτη |
| Λογαριασμός πελάτη | «το κατάστημά μου» (ήδη υπάρχει `Customer.storeId`): προτεραιότητα σε αυτό |

**Ταχύτητα**: οι σελίδες είναι server components και διαβάζουν από την τοπική βάση με το υπάρχον swr cache, με tag ανά προϊόν. Η projection στέλνει μόνο αλλαγές και σβήνει μόνο τα σχετικά tags, άρα καμία κλήση προς τη μηχανή σε προβολή σελίδας.

**Αν πέσει η μηχανή**: το eshop συνεχίζει με τα τελευταία στοιχεία. Όσα ξεπερνούν το όριο φρεσκάδας (π.χ. 24 ώρες) κρύβονται αυτόματα, γιατί το φίλτρο είναι `seenAt > now − όριο`. Η live επιβεβαίωση στο checkout γυρίζει σε «επιβεβαίωση από το κατάστημα». Το eshop δεν σταματά ποτέ εξαιτίας της μηχανής.

### Reporting
Τα αναλυτικά (runs, σφάλματα, φρεσκάδα ανά μέλος, ποσοστό αντιστοίχισης) τα υπολογίζει η μηχανή και τα εκθέτει ως API. Το κεντρικό admin τα εμφανίζει. Οι επιχειρησιακές αναφορές (π.χ. «πόσες πωλήσεις eshop έδειξαν διαθεσιμότητα μέλους») βγαίνουν από το read model στο κεντρικό, χωρίς join ανάμεσα στις δύο βάσεις.

### Εναλλακτικές που εξετάστηκαν
| | Πώς | Υπέρ | Κατά |
|---|---|---|---|
| Α. Όλα σε μία εφαρμογή + μία βάση | `StoreStock` όπως σήμερα | απλό | φορτώνει την κοινή βάση· τα secrets δίπλα στους πελάτες· μια κολλημένη σύνδεση επηρεάζει το eshop |
| Β. Ίδια εφαρμογή, **χωριστή βάση + χωριστός worker** | ίδιο repo, δεύτερο Prisma schema, worker ως δεύτερη υπηρεσία Coolify, push API στο κεντρικό domain | λιγότερο ops, κοινός κώδικας | το δημόσιο push API μοιράζεται host με το eshop· η απομόνωση είναι μισή |
| **Γ. Χωριστή υπηρεσία + βάση + subdomain** (επιλογή) | όπως το διάγραμμα | πλήρης απομόνωση φορτίου, βλαβών και secrets | δύο deploys, συμβόλαιο API ανάμεσά τους |
| Δ. Το eshop ρωτά live τη μηχανή | χωρίς projection, API + cache | ένα σημείο αλήθειας | καθυστέρηση και εξάρτηση σε κάθε προβολή σελίδας· δύσκολα φίλτρα/facets |

**Πρόταση υλοποίησης της Γ:** ίδιο repo (monorepo: `apps/web`, `apps/stock`, `packages/contracts` με τους κοινούς τύπους και τα σχήματα γεγονότων), δύο υπηρεσίες στο Coolify, δεύτερη βάση σε **άλλο Postgres instance** (ή στην αρχή χωριστή database στον ίδιο server με δικό της όριο συνδέσεων, και μεταφορά όταν μεγαλώσει). Το push API και οι workers ζουν στο `stock.euronics.gr`.

## 2. Μοντέλο οντοτήτων

```
Partner (νομικό πρόσωπο, ΑΦΜ) ──1:N── Store (υπάρχον, γεωγραφικά)
   │                                    │
   ├──1:N── PartnerContact ──0:1── B2bAccount (κωδικός, ρόλος, καταστήματα)
   ├──1:N── QuestionnaireResponse ──> QuestionnaireTemplate (εκδόσεις)
   ├──1:N── Connection ──1:N── ConnectionTest
   │            └── (Φάση 2+) ConnectionRun, PartnerProductLink, LocationMap
   ├──1:N── ProfileChange (προς έγκριση)
   └──0:1── S1 link (TRDR) · Store ↔ TRDBRANCH · Contact ↔ TRDPRSN

PartnerApplication (εκδήλωση ενδιαφέροντος, δημόσια) ──μετατροπή──> Partner
B2bInvite (σύνδεσμος δημιουργίας/πρόσκλησης, token) ──> B2bAccount
```

### Οντότητες

**Partner** — το μέλος/συνεργάτης ως εταιρεία.
- Ταυτότητα: επωνυμία, διακριτικός τίτλος, ΑΦΜ (μοναδικό), ΔΟΥ (`TaxOffice`), έδρα, τηλ., email, website.
- Κατάσταση κύκλου ζωής: `lead → onboarding → connecting → live → suspended`.
- `s1Trdr` (μοναδικό, nullable), `s1SyncStatus`, `s1SyncedAt`, `s1LastError`.
- `systems` (σύνοψη από το ερωτηματολόγιο: ERP, eshop, εκδόσεις) για γρήγορο φιλτράρισμα στη λίστα.

**Store** (υπάρχον) — **ένα Store ανά υποκατάστημα SoftOne (TRDBRANCH)**, γιατί η διαθεσιμότητα αναφέρεται σε υποκατάστημα. Όλα τα μέλη και όλα τα υποκαταστήματα εμφανίζονται στο eshop: τα ~320 υποκαταστήματα αντί για τα 252 σημερινά, συμπεριλαμβανομένων των μελών «E-shop» και του «ΠΡΟΜΗΘΕΥΤΗΣ». Μέλος χωρίς υποκατάστημα (~28) → ένα Store από τη διεύθυνση του πελάτη. Προσθήκες: `partnerId`, `s1BranchId` (TRDBRANCH), `publishedProfile` vs πρόχειρο (βλ. §5), `stockVisible` (αν δείχνουμε τη διαθεσιμότητά του στο eshop).

**PartnerContact** — πρόσωπο επαφής: ονοματεπώνυμο, ιδιότητα (ιδιοκτήτης, υπεύθυνος καταστήματος, IT, λογιστήριο), email, κινητό, τηλ., καταστήματα που αφορά, `s1PrsnId` (TRDPRSN), συναινέσεις επικοινωνίας. Προσωπικά δεδομένα → GDPR (εξαγωγή/διαγραφή μαζί με τις υπόλοιπες ροές).

**B2bAccount** — η πρόσβαση μιας επαφής στην πύλη. Χωριστό από την επαφή, ώστε να υπάρχουν επαφές χωρίς είσοδο.
- `email` (μοναδικό στο realm B2B), `passwordHash` (μόνο εδώ — **δεν** πάει στο SoftOne), `active`, `lastLoginAt`, `mustChangePassword`.
- Ρόλος μέσα στον συνεργάτη: `owner` (όλα), `manager` (προφίλ + σύνδεση για τα καταστήματά του), `viewer` (μόνο ανάγνωση).
- Εμβέλεια: όλα τα καταστήματα του συνεργάτη ή υποσύνολο.
- 2FA: OTP στο email όπως στο Staff (προαιρετικό στην αρχή, υποχρεωτικό για `owner`).

**B2bInvite** — σύνδεσμος μιας χρήσης (token hash, λήξη 7 ημέρες, ποιος τον έστειλε, για ποια επαφή/συνεργάτη ή «νέο»). Οδηγεί σε ορισμό κωδικού ή σε προσυμπληρωμένη αίτηση.

**B2bPasswordReset / B2bLoginChallenge** — ίδια δομή με `PasswordReset` / `StaffLoginChallenge`, χωριστοί πίνακες (χωριστό realm, χωριστά όρια).

**PartnerApplication** — δημόσια φόρμα «θέλω να ενταχθώ»: εταιρεία, ΑΦΜ, καταστήματα (πόλη), επαφή, συστήματα που χρησιμοποιεί (ελεύθερη επιλογή), μήνυμα, συναίνεση, πηγή (`organic`, `invite:<id>`, `referral:<customerId>`). Κατάσταση `new → contacted → approved → converted | rejected`. Η μετατροπή φτιάχνει Partner + Contact + (προαιρετικά) πρόσκληση· αν βρεθεί ίδιος ΑΦΜ σε υπάρχοντα Partner ή στο SoftOne, συνδέεται αντί να διπλασιαστεί.

**QuestionnaireTemplate / QuestionnaireResponse**
- Πρότυπο με εκδόσεις, ορισμένο ως JSON (ενότητες, ερωτήσεις, τύπος, υποχρεωτικό, **συνθήκες εμφάνισης** — π.χ. οι ερωτήσεις Entersoft εμφανίζονται μόνο αν επιλεγεί Entersoft). Το επεξεργαζόμαστε από το admin χωρίς deploy.
- Απάντηση ανά συνεργάτη: `answers` JSON, `templateVersion`, κατάσταση `draft → submitted → reviewed → needs-info`, σχόλια ανά ερώτηση από εμάς. Αυτόματη αποθήκευση πρόχειρου.
- Από τις απαντήσεις προκύπτει **πρόταση τρόπου σύνδεσης** (κανόνες, όχι AI): π.χ. «SoftOne + Web Services ανοιχτά → SoftOne WS», «μόνο WooCommerce → Woo REST», «τίποτα από τα παραπάνω → αρχείο Excel/CSV ή push API».

**Connection** — ένας τρόπος διασύνδεσης ανά συνεργάτη (συνήθως ένας· επιτρέπονται περισσότεροι, π.χ. ERP για 3 καταστήματα + eshop για 1).
- `type` (βλ. §4), `config` JSON (μη ευαίσθητα: URL, serial, εταιρεία/υποκατάστημα, όνομα αποθήκης), `secrets` κρυπτογραφημένα (AES‑GCM με κλειδί από env· δεν επιστρέφονται ποτέ στο UI — μόνο «έχει οριστεί / αντικατάσταση»).
- `stores` που καλύπτει, `status` `draft → testing → ok | failed → active | paused`, `lastTestAt`, `lastOkAt`.
- **ConnectionTest**: ιστορικό ελέγχων με βήματα (`reach`, `auth`, `read-sample`, `locations`), διάρκεια, μήνυμα σφάλματος σε απλά ελληνικά, δείγμα 5 γραμμών (χωρίς προσωπικά δεδομένα).

**ProfileChange** — αλλαγή του συνεργάτη στο δημόσιο προφίλ καταστήματος, προς έγκριση (βλ. §5).

## 3. Τρεις «κόσμοι» χρηστών, τρία realms

| Realm | Ποιος | Είσοδος | Cookie/συνεδρία |
|---|---|---|---|
| Admin | Staff | κωδικός + OTP (υπάρχον) | υπάρχον Auth.js |
| **B2B** | B2bAccount | κωδικός + OTP (ίδιο pattern) | **χωριστό** cookie (`b2b_session`), χωριστό secret, μικρότερη διάρκεια |
| Eshop | Customer | υπάρχον | υπάρχον |

Κανόνες:
- Κάθε ερώτημα στο B2B φιλτράρει **πάντα** με `partnerId` (και `storeIds` της εμβέλειας) από τη συνεδρία — ποτέ από παράμετρο URL. Ένας κεντρικός guard `requireB2b({ role, storeId? })` όπως το `can()`.
- Rate limiting σε είσοδο, ανάκτηση, αίτηση, πρόσκληση (υπάρχον `throttle`). Ουδέτερα μηνύματα («αν υπάρχει λογαριασμός, στάλθηκε email») για να μη φαίνεται ποια emails υπάρχουν.
- Κάθε ενέργεια του συνεργάτη και δική μας πάνω σε συνεργάτη → `AuditLog` με `actorType: staff | b2b`.
- Ένας Staff μπορεί να «δει ως» συνεργάτης (impersonation μόνο ανάγνωσης, καταγράφεται) για υποστήριξη.

## 4. Τρόποι διασύνδεσης (πλαίσιο connectors)

Κοινή διεπαφή κάθε connector (υλοποιείται σε επόμενες φάσεις, ορίζεται τώρα):

```
test(config, secrets)        → βήματα reach / auth / read-sample, αποτέλεσμα σε απλά ελληνικά
listLocations()              → οι αποθήκες/υποκαταστήματα του συστήματός τους (για αντιστοίχιση με Store)
fetchStock(since?)           → κανονικοποιημένες γραμμές:
                               { externalSku, ean?, mpn?, brand?, title?, locationRef, qty, updatedAt? }
```

| Τύπος | Πώς | Έλεγχος στη Φάση 1 |
|---|---|---|
| `softone-ws` | Επίσημα S1 WS (login → authenticate, κλειδί ημέρας), browser/`SqlData` στοκ ανά αποθήκη | ✅ login+authenticate+δείγμα |
| `entersoft` | Entersoft Business Suite / EBS web API (μέθοδοι ορίζονται με το IT τους) | ⏳ μόνο reach/auth αν δοθεί endpoint |
| `epsilon` | Epsilon Net (Pylon/Business) — API ή εξαγωγή | ⏳ συνήθως → αρχείο ή push |
| `galaxy` | SingularLogic Galaxy — API ή εξαγωγή | ⏳ συνήθως → αρχείο ή push |
| `woocommerce` | WC REST (read-only, ck/cs) | ✅ auth + 5 προϊόντα με `stock_quantity` |
| `shopify`, `magento`, `opencart`, `prestashop` | αντίστοιχα REST | ⏳ ανά ζήτηση |
| `feed-url` | XML/CSV/JSON σε URL (ίδιο wizard με τους προμηθευτές) | ✅ λήψη + ανάλυση + αντιστοίχιση στηλών |
| `sftp` / `email-drop` | αρχείο που ανεβάζουν περιοδικά | ⏳ |
| `push-api` | **αυτοί** στέλνουν σε εμάς `POST /api/b2b/v1/stock` με κλειδί | ✅ «στείλτε δοκιμαστικό αίτημα» και η σελίδα το δείχνει live |
| `manual` | ανέβασμα Excel από την πύλη | ✅ ανέβασμα + προεπισκόπηση |

Σημειώσεις σχεδιασμού:
- **Pull vs push**: προτιμάμε pull όπου υπάρχει API (ελέγχουμε εμείς τη συχνότητα)· push για κλειστά ERP χωρίς δημόσιο endpoint — τους δίνουμε προδιαγραφή και κλειδί, και το IT τους (ή ο τεχνικός του ERP) γράφει ένα μικρό job.
- **Ασφάλεια διαπιστευτηρίων**: ζητάμε πάντα χρήστη **μόνο ανάγνωσης** (το ερωτηματολόγιο το εξηγεί)· δεν αποθηκεύουμε κωδικούς σε απλό κείμενο· τα secrets δεν εμφανίζονται ποτέ ξανά.
- **Επιτυχής έλεγχος** = auth OK **και** διαβάστηκαν γραμμές στοκ **και** αντιστοιχίστηκε ≥1 τοποθεσία τους σε κατάστημά μας. Μέχρι τότε η σύνδεση δεν γίνεται `active`.

### Η διαφορετική κατηγοριοποίηση (για τις επόμενες φάσεις)
Για τη διαθεσιμότητα **δεν χρειάζεται αντιστοίχιση κατηγοριών** — χρειάζεται αντιστοίχιση **προϊόντος**. Σειρά:
1. EAN/barcode (το πιο συχνό στα ηλεκτρικά),
2. κωδικός κατασκευαστή + μάρκα (κανονικοποιημένος, όπως κάνουμε ήδη στα feeds),
3. ο δικός μας κωδικός, αν ο συνεργάτης τον κρατά στο ERP του (ρωτιέται στο ερωτηματολόγιο),
4. AI/ασαφής με **έγκριση** — ποτέ αυτόματα.
Αποτέλεσμα: `PartnerProductLink (partnerId, externalSku → variantId, method, confidence, status)`, που μένει και δεν ξαναϋπολογίζεται. Οι κατηγορίες τους κρατιούνται μόνο ως βοήθημα για τα αταίριαστα.
